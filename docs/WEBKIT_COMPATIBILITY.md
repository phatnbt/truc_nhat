# P708 Safari and WebKit compatibility baseline

Verified 2026-11-27. P708 source references describe checkout commit `54d91aa`. Safari/iOS **15.4** is the native floor for the two built-ins below. Safari/iOS **27.0** is the first stable release with the conformant top-level `await` loader. A P708 support floor also requires device evidence.

## JavaScript startup

- **Top-level `await`.** MDN BCD records partial support in Safari and iOS Safari from **15.0 through 26.x**. On the old loader, overlapping imports of the same module suspended at top-level `await` could resolve before evaluation finished, exposing uninitialized exports and throwing a `ReferenceError`. WebKit landed the rewrite on **April 14, 2026** in `311236@main`, shipped it in **Safari Technology Preview 243** on **May 7**, and shipped the stable fix in **Safari 27.0 (20625.1.29)** on **September 14, 2026**, including **iOS/iPadOS 27.0**. [MDN BCD](https://github.com/mdn/browser-compat-data/blob/main/javascript/operators/await.json#L79-L93) · [WebKit bug 242740](https://bugs.webkit.org/show_bug.cgi?id=242740#c16) · [STP 243](https://webkit.org/blog/17953/release-notes-for-safari-technology-preview-243/#javascript) · [WebKit loader explanation](https://webkit.org/blog/18227/fixing-top-level-await-in-safari/) · [Apple Safari 27 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes)
- **P708 boot and built-ins.** The checked-in entry module awaits a dynamic import at top level. That makes Safari below 15.0 a startup syntax risk. On 15.0–26.x, attributing a failure to bug 242740 requires evidence of overlapping imports of a suspending module and the matching initialization error. `Array.prototype.at()` and `Object.hasOwn()` both first ship in **Safari and iOS Safari 15.4**. On earlier versions, an unguarded call can throw when its code path executes. [P708 entry module](../app.js) · [MDN BCD for `at()`](https://github.com/mdn/browser-compat-data/blob/main/javascript/builtins/Array.json#L115-L151) · [MDN BCD for `hasOwn()`](https://github.com/mdn/browser-compat-data/blob/main/javascript/builtins/Object.json#L978-L1014)
- **Build targets.** Browserslist has separate `safari` and `ios_saf` targets. Babel preset-env uses those targets for compiled input. Built-in polyfills are supplied via `core-js` integration in Babel 7 or a polyfill plugin in Babel 8. Babel's top-level `await` support is parsing only. Direct CDN imports execute the delivered modules in the browser. [Browserslist](https://github.com/browserslist/browserslist#browsers) · [Babel preset-env](https://babeljs.io/docs/babel-preset-env#usebuiltins-corejs) · [Babel top-level await](https://babeljs.io/docs/babel-plugin-syntax-top-level-await) · [Firebase CDN setup](https://firebase.google.com/docs/web/alt-setup#from-the-cdn)

## Visibility, storage and Firebase

- **Lifecycle signals.** WHATWG defines `visibilitychange` on `document` for `visible`/`hidden` transitions and `pagehide`/`pageshow` for page transitions. BCD records partial `visibilitychange` in older Safari, including missing events on navigation away before desktop Safari **14.1**. IndexedDB transactions are short-lived and may commit or abort before resume. WebKit bug 202705 records an iOS 13 suspension case. WebKit also documents that iOS/iPadOS **17.2** began copying cookies on Home Screen installation, with IndexedDB and other local storage outside that copy. [WHATWG visibility](https://html.spec.whatwg.org/multipage/interaction.html#page-visibility) · [WHATWG page transitions](https://html.spec.whatwg.org/multipage/nav-history-apis.html#the-pagetransitionevent-interface) · [MDN BCD](https://github.com/mdn/browser-compat-data/blob/main/api/Document.json#L9139-L9169) · [IndexedDB transaction lifecycle](https://w3c.github.io/IndexedDB/#transaction-lifetime-concept) · [WebKit bug 202705](https://bugs.webkit.org/show_bug.cgi?id=202705) · [WebKit 17.2](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/#login-cookies)
- **Published Firebase support.** P708 pins the modular App, Auth and Firestore CDN files to **12.16.0**. All three public URLs returned HTTP 200 with a JavaScript content type. Firebase released 12.16.0 on **July 9, 2026** and moved the SDK to **ES2020** in **12.0.0**. Its general support matrix lists Auth and Firestore on Safari and iOS Safari, calls for needed polyfills, and qualifies Firestore persistence below iOS 10. The matrix and release notes give no Safari minimum specific to the 12.16.0 CDN files. Web Firestore persistent caching is opt-in, and the checked-in P708 engine uses memory cache. [App CDN](https://www.gstatic.com/firebasejs/12.16.0/firebase-app.js) · [Auth CDN](https://www.gstatic.com/firebasejs/12.16.0/firebase-auth.js) · [Firestore CDN](https://www.gstatic.com/firebasejs/12.16.0/firebase-firestore.js) · [12.16.0 release](https://firebase.google.com/support/release-notes/js#version_12160_-_july_9_2026) · [12.0.0 release](https://firebase.google.com/support/release-notes/js#version_1200_-_july_17_2025) · [Supported environments](https://firebase.google.com/docs/web/environments-js-sdk#browsers) · [Firestore offline cache](https://firebase.google.com/docs/firestore/manage-data/enable-offline) · [P708 sync engine](../src/core/p708-secure-sync-engine.js)
- **Auth resume fixes.** Firebase **12.18.0** fixed a popup/background-tab “Database is closing/hidden” failure. **12.19.0** added on-demand IndexedDB reconnection after `pagehide` for `signInWithPopup` on iOS/iPadOS Safari. Both releases postdate the pin. Match the failing Auth operation and error before attributing a P708 resume incident to either fix. [Firebase 12.18.0](https://firebase.google.com/support/release-notes/js#version_12180_-_august_19_2026) · [Firebase 12.19.0](https://firebase.google.com/support/release-notes/js#version_12190_-_september_9_2026)

## Audit verification

The recovery build moves async work into functions, removes the app's calls to the two Safari 15.4 built-ins and retains the Firebase 12.16.0 pin. Start physical compatibility verification on **iOS 16.4** and a current iOS as separate targets. Safari 16.4 is a practical starting point for verifying the optional features, including Home Screen Web Push. The minimum supported iOS for the complete P708 workflow remains unverified. [WebKit Safari 16.4 release](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/#web-push-on-ios-and-ipados)

Playwright uses a patched WebKit build from upstream sources. Its iPhone profiles emulate properties such as viewport, touch and user agent. A pass covers the tested engine and configuration. Safari tab and installed Home Screen behavior across OAuth, backgrounding, lock and process termination still require physical iPhone evidence. Record the exact iOS version, app release, mode and first error when comparing a pre-27 device with a 27.0-or-later control.
